# محدودیت‌ها و نقشه راه مقیاس‌پذیری

## ۱) آنچه امروز کار می‌کند

* کشف چندمنبعی (موتور جستجو، دایرکتوری، داده عمومی، سایت شرکت، پیکره آفلاین)
* برنامه‌ریز پرس‌وجو بر پایه سلسله‌مراتب استان→شهرستان→شهر با قالب‌های خودکار
* استخراج با شاهد (JSON-LD، بلوک دایرکتوری، متن صفحه، لینک tel)
* موتور شماره (نرمال‌سازی، پیش‌شماره، کیفیت، تشخیص جعلی/خدماتی/مصنوعی)
* ارتباط‌سنجی و رد متن نامرتبط + تشخیص صفحه اسپم
* امتیاز اعتبار ۰..۱۰۰ با باند و ریزاجزای قابل بازبینی
* یکتاسازی محافظه‌کار با لنگر هویتی و حفظ همه منابع
* پایگاه داده ۱۹ جدولی + صف/کارگر + تلاش مجدد + محدودیت نرخ
* API + داشبورد + خروجی CSV/Excel/JSON با فیلتر کامل
* آزمون‌های واحد، یکپارچه و سرتاسری (۵۵ آزمون) + ۸ معیار پذیرش

## ۲) محدودیت‌های شناخته‌شده (صادقانه)

| محدودیت | اثر | راه‌حل پیشنهادی |
|---|---|---|
| اعتبارسنجی «واقعی» شماره (تماس/پیامک) انجام نمی‌شود | وضعیت شماره ساختاری است (`VALID` = قالب و زمینه درست) نه «پاسخ‌دهنده» | افزودن ماژول Validation با درگاه SMS/IVR در فاز بعد |
| کشف زنده اینترنت در این محیط آزمون نشده | عدم اثبات کارکرد منابع واقعی | اجرای `make test-live` روی شبکه آزاد + پایش نرخ موفقیت منابع |
| داده مرجع همراه برنامه ۳۸۰ شهرستان/۵۵۴ شهر است | پوشش نام کامل شهرها با `fetch-geo` به دست می‌آید | اجرای `fetch-geo` در استقرار (۴۸۴/۱۴۸۱) |
| تطبیق نام مکان با تطبیق رشته‌ای انجام می‌شود | نام‌های نویسه‌ای خاص ممکن است تطبیق نیابند | افزودن جدول نام‌های جایگزین/املای رسمی |
| شماره مشترک واقعی (چند شعبه) باعث خطای معیار «بدون تکرار» می‌شود | در دموی آفلاین پذیرفته نمی‌شود | افزودن جدول استثنا برای تلفن‌های مشترک سازمانی |
| نام مالک فقط از متن عمومی | بسیاری از رکوردها `owner_status = NOT_FOUND` | توصیه: تکیه بر داده رسمی/صنفی، نه حدس |
| SQLite برای نوشتن موازی محدود است | با کارگرهای زیاد، قفل رخ می‌دهد | تغییر به PostgreSQL (`NUMBERBANK_DATABASE_URL`) |

## ۳) مسیر مقیاس‌پذیری تا میلیون‌ها رکورد

### الف) دیتابیس
* **PostgreSQL** با پارتیشن‌بندی جدول `source_observations` بر اساس ماه (بزرگ‌ترین جدول).
* ایندکس‌های تأییدشده موجود: `businesses.fingerprint`، `phones.e164`، `source_observations.dedupe_hash`،
  `search_queries(source_key, query_hash)`، `business_phones(business_id, phone_id)`.
* افزودنی‌های لازم: ایندکس GIN روی `name_key` (trigram) برای جستجوی فازی، ایندکس جزئی روی
  `confidence_band`، و `BRIN` روی `observed_at`.
* آرشیو سرد: انتقال شواهد قدیمی‌تر از ۲ سال به جدول/انبار جدا.

### ب) صف و کارگر
* جایگزینی صف SQLite با **Redis Streams / RabbitMQ / Celery** برای توزیع چندسروری.
* تفکیک کارگرها: `fetch` (خزش)، `extract` (استخراج)، `validate` (بازاعتبارسنجی)، `dedup` (ادغام).
* بودجه‌بندی نرخ در سطح دامنه (token bucket) و احترام سخت‌گیرانه به `robots.txt`.
* کش HTTP مشترک (Redis) برای پرهیز از دریافت مکرر همان صفحه.

### ج) خزش و منابع
* افزودن منابع صنفی رسمی (اتحادیه‌ها، سامانه‌های مجوز) به‌جای تکیه بر موتور جستجو.
* خزنده نقشه‌محور (sitemap-first) برای سایت شرکت‌ها به‌جای جستجو در هر اجرا.
* موازی‌سازی چند پروفایل پروکسی با محدودیت نرخ هر خروجی.
* کشف تدریجی: هر اجرا فقط «شهرهای بدون داده یا کم‌داده» را هدف بگیرد (پیش‌فرض فعلی).

### د) کیفیت و الگوریتم
* افزودن مدل زبانی سبک برای استخراج نام/نشانی از متن‌های بی‌ساختار (با حفظ قاعده «بدون شاهد،
  بدون رکورد»).
* امتیاز اعتبار وزنی‌تر: اعتبار دامنه، قدمت صفحه، هم‌راستایی نشانی و پیش‌شماره، تنوع منبع.
* تشخیص کپی‌برداری صفحه با هش محتوا و شباهت متنی.

### ه) عملیات
* اجرای زمان‌بندی‌شده (cron/Kubernetes CronJob) برای `worker --once` و `revalidate`.
* پایش: نرخ موفقیت هر منبع، نرخ رد نامرتبط، نرخ ادغام، زمان چرخه، عمق صف.
* پشتیبان‌گیری دوره‌ای + تست بازیابی؛ نسخه‌بندی مهاجرت‌ها (Alembic) پیش از تغییر مدل.

## ۴) برآورد سرانگشتی

| مقیاس | حجم تقریبی | زیرساخت پیشنهادی |
|---|---|---|
| ۱۰ هزار رکورد | ~۵۰ هزار شاهد | یک سرور کوچک + SQLite کافی است |
